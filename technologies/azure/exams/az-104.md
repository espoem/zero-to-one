### Q-AZ104-001 · Manage Azure identities and governance · difficulty 2 · scenario

A virtual machine in Sweden Central stops accepting tag updates and policy re-evaluations while its workload keeps serving traffic; the resource group that contains it was created in France Central, where an Azure Resource Manager metadata outage is in progress. What is the correct explanation and mitigation?

- A) The VM's regional resource provider is down, so the VM must be redeployed to another region.
- B) Resource group metadata is served from the resource group's home region, so control-plane writes that touch the group fail while the VM's data plane and its regional resource provider stay healthy; wait for the metadata region to recover, because the group's location cannot be changed.
- C) The resource group can be moved to Sweden Central with `az group update --location` to restore control-plane writes.
- D) The VM is unaffected by the outage, so the failure must be an RBAC propagation delay that re-assigning the role will fix.

<details><summary>Answer</summary>

**B.** A resource group is a metadata container whose records live in the location chosen at creation. That location does not constrain where resources run, but control-plane operations that read or write group metadata depend on that partition, which is why a French metadata outage blocks tag writes on a Swedish VM.

- Why not A: the guest and its data plane are still serving, so this is not a regional compute-provider failure.
- Why not C: a resource group's location is fixed at creation; moving resources creates a different group.
- Why not D: an RBAC delay would not coincide with a regional ARM metadata outage, and role assignment writes use the same metadata partition.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/manage-resource-groups-portal

</details>

### Q-AZ104-002 · Manage Azure identities and governance · difficulty 2 · scenario

You assign an initiative containing a `DeployIfNotExists` definition for diagnostic settings to a subscription with 4,000 existing resources. Compliance reports 3,900 non-compliant resources, no diagnostic settings appear after 48 hours, and resources created after the assignment are compliant. What must you do?

- A) Change the assignment's `enforcementMode` from `DoNotEnforce` to `Default`.
- B) Change the definition's effect from `DeployIfNotExists` to `Append`.
- C) Re-assign the initiative separately at each resource group that contains non-compliant resources.
- D) Create a remediation task for the assignment and grant its managed identity a role that can create the dependent resource, such as `Monitoring Contributor`, at the assignment scope.

<details><summary>Answer</summary>

**D.** `DeployIfNotExists` is a request-time effect: it runs when a resource is created or updated through ARM and never retroactively. Pre-existing resources stay non-compliant until a remediation task runs, and that task acts as the assignment identity, which therefore needs permission to write the dependent resource type.

- Why not A: enforcement mode controls whether an effect blocks or is skipped, not whether it is applied to existing resources.
- Why not B: `Append` also runs at request time and can only add fields to the primary resource, not create a child resource.
- Why not C: per-group assignments change nothing for resources that already exist and multiply the assignment count.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/governance/policy/how-to/remediate-resources

</details>

### Q-AZ104-003 · Manage Azure identities and governance · difficulty 3 · scenario

A storage account has an inherited `ReadOnly` lock. Applications using a managed identity with `Storage Blob Data Contributor` continue to read and write blobs, but Storage Explorer and an account-key ETL job fail, and `az storage account keys list` returns HTTP 409 Conflict (`ScopeLocked`). Which statement explains the behaviour?

- A) The lock blocks all writes, so the applications must be failing silently against a cached copy.
- B) The lock applies only to the resource group, so a separate policy assignment must be blocking the keys.
- C) The lock rejects write-classified ARM requests, including the `listKeys` POST action, so account-key consumers cannot obtain a key, while Entra ID data-plane requests never traverse ARM and keep working.
- D) The lock affects only the portal; CLI key retrieval uses a data-plane endpoint outside the lock's scope.

<details><summary>Answer</summary>

**C.** A lock is an ARM control-plane construct. `Microsoft.Storage/storageAccounts/listKeys/action` is classified as a write, so `ReadOnly` rejects it with HTTP 409 Conflict (`ScopeLocked`), and every tool that defaults to account-key authentication fails. Blob requests go to `*.blob.core.windows.net` with an Entra ID token and never touch ARM, so they succeed.

- Why not A: blob writes genuinely work, which is exactly the asymmetry that confuses operators.
- Why not B: locks inherit from the resource group to the account, and no second policy is needed to explain the `409 ScopeLocked` rejection.
- Why not D: `listKeys` is an ARM action, which is precisely what the lock evaluates.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/lock-resources

</details>

### Q-AZ104-004 · Manage Azure identities and governance · difficulty 2 · single

An administrator with `Owner` on a storage account receives `403 AuthorizationPermissionMismatch` when reading a blob with their own Entra ID identity, while reading with the account key succeeds. What is the reason?

- A) `Owner` includes data actions but requires just-in-time activation through PIM.
- B) `Owner` is a control-plane role that contains no blob data actions, so a role such as `Storage Blob Data Reader` is required.
- C) `Owner` grants data access only through the Azure portal, and CLI access always needs a SAS token.
- D) The account has `allowSharedKeyAccess: false`, which blocks every Entra ID read.

<details><summary>Answer</summary>

**B.** Azure separates the control plane from the data plane. `Owner` grants full management of the account object and no blob actions, so the data plane returns `AuthorizationPermissionMismatch` until a `Storage Blob Data *` role is assigned at or above the container scope.

- Why not A: `Owner` contains no data actions at all, so no activation can add them.
- Why not C: the portal calls the same blob data-plane API with the same token.
- Why not D: the effect is inverted; disabling shared key removes the key path and leaves Entra ID as the working path.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access

</details>

### Q-AZ104-005 · Manage Azure identities and governance · difficulty 3 · scenario

You assign `Storage Blob Data Contributor` to a group at storage-account scope and add a developer to the group. Two hours later the developer's `az storage blob list` still fails with 403, although roles granted last week work. The developer signed in before the membership change and has not signed out. What is the most likely cause?

- A) The access token was issued before the membership change and still carries the old group claims, so the developer must re-authenticate and acquire a fresh token before the assignment is treated as broken.
- B) Azure RBAC assignments take 24 hours to propagate, so no action is needed.
- C) Group-based assignments never apply to data-plane roles, so only direct user assignments work.
- D) Storage data roles cannot be assigned at account scope and must be assigned per container.

<details><summary>Answer</summary>

**A.** Role assignment propagation is normally seconds to minutes with a documented worst case around 30 minutes, and two hours have already elapsed. What remains is the token: group membership is baked into the token at issue time, and a token minted before the change keeps the old claim set until it is refreshed.

- Why not B: the 24-hour claim is false, and waiting longer does not refresh an existing token.
- Why not C: group assignments do authorize data-plane roles; the known caveat is that some ABAC condition features do not support group principals.
- Why not D: account-scope assignment is the standard way to grant access across every container in the account.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/azure/role-based-access-control/troubleshooting

</details>

### Q-AZ104-006 · Manage Azure identities and governance · difficulty 3 · scenario

A subscription has reached its role-assignment limit during a migration. A colleague proposes requesting a quota increase and continuing per-user assignments at resource-group scope for 1,200 engineers across 40 resource groups. What is the correct assessment?

- A) The quota increase will be granted, and per-user assignment is the recommended least-privilege model at that scale.
- B) The 4,000 limit applies per resource group, so assigning at resource-group scope avoids it.
- C) Deleting and recreating the subscription is the supported way to reset the counter.
- D) There is no general quota increase for role assignments; the proposal implies 48,000 assignments, so the design must move to group-based assignment at higher scopes, fewer scopes, and ABAC conditions where per-object granularity is genuinely required.

<details><summary>Answer</summary>

**D.** The published ceilings are 4,000 role assignments per subscription and 500 per management group. The arithmetic is diagnostic: 1,200 engineers times 40 resource groups is 48,000 assignments, twelve times the ceiling before any platform role exists, which means the model is per-user and must change rather than be enlarged.

- Why not A: the ceiling is a platform limit rather than a soft quota, and per-user models grow linearly with headcount.
- Why not B: the limit is per subscription, so splitting scope does not help.
- Why not C: a new subscription starts empty but is not a migration strategy and discards the audit trail.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/azure/role-based-access-control/troubleshooting

</details>

### Q-AZ104-007 · Manage Azure identities and governance · difficulty 3 · single

Forty analysts must read only blobs in containers whose names begin with `finance-` in one storage account, using as few role assignments as possible. Which configuration achieves this?

- A) Assign `Storage Blob Data Reader` on each of the 40 containers for each analyst.
- B) Assign `Storage Blob Data Reader` at the storage account with an ABAC condition that checks `ContainerName` with `StringStartsWith`, after confirming the role supports conditions.
- C) Create 40 custom roles whose `AssignableScopes` point at each container.
- D) Assign `Storage Blob Data Owner` at the account and rely on container ACLs to restrict access.

<details><summary>Answer</summary>

**B.** Attribute-based access control conditions on blob data roles can filter on container name or blob prefix, so a single assignment at account scope expresses the whole rule and stays correct as containers are added.

- Why not A: 40 containers times 40 analysts is 1,600 assignments before any other role exists.
- Why not C: `AssignableScopes` is a list of management scopes, and a container is not a valid assignable scope for a role definition.
- Why not D: the owner role is far broader than read, and POSIX ACLs do not restrict blob access through the RBAC path.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/azure/role-based-access-control/conditions-overview

### Q-AZ104-008 · Manage Azure identities and governance · difficulty 2 · scenario

A GitHub Actions workflow must deploy Bicep to Azure with no stored credential, and only runs on the `main` branch of `org/repo` may obtain a token. Which configuration is correct?

- A) Create a service principal secret, store it as a GitHub secret, and rotate it every 90 days.
- B) Enable a system-assigned managed identity on the GitHub-hosted runner and grant it `Owner` at the tenant root.
- C) Create an app registration with a federated credential for the GitHub OIDC issuer whose subject is `repo:org/repo:ref:refs/heads/main`, grant it the deployment role at the target scope, and let the workflow exchange its OIDC token for an Entra ID token.
- D) Create a user-assigned managed identity and store its client secret in Key Vault for the workflow to read at deploy time.

<details><summary>Answer</summary>

**C.** Workload Identity Federation lets an external identity provider's token be exchanged for a short-lived Entra ID token. Pinning the federated credential's subject to the protected branch means a pull-request workflow cannot obtain the same token even inside the same repository.

- Why not A: a stored long-lived secret is what federation removes, and rotation does not prevent exfiltration between rotations.
- Why not B: GitHub-hosted runners are not Azure VMs and cannot carry a managed identity, and tenant-root `Owner` is reckless.
- Why not D: that reintroduces a secret plus a bootstrap credential problem.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation

### Q-AZ104-009 · Manage Azure identities and governance · difficulty 2 · single

A `Deny` policy assigned at a management group blocks a required public IP SKU in one subscription. You must unblock only that subscription while keeping an auditable record of why. Which approach is correct?

- A) Create a policy exemption of type `Waiver` at the subscription scope with a justification and expiry date, and keep the assignment in place.
- B) Set `enforcementMode` to `DoNotEnforce` on the management-group assignment.
- C) Delete the policy definition and recreate it at the subscription scope.
- D) Add the subscription to the assignment's `notScopes`, because exclusions are auditable and exemptions are not.

<details><summary>Answer</summary>

**A.** An exemption keeps the scope inside the assignment, records a justification and an expiry, and reports the resource as exempt while `Deny` is bypassed. That is the only one of these options that both unblocks and leaves an audit trail.

- Why not B: `DoNotEnforce` disables the effect for every subscription under the management group.
- Why not C: definitions are inert without an assignment, and recreating at a narrower scope multiplies assignments and loses central reporting.
- Why not D: `notScopes` excludes silently and records neither justification nor expiry, which fails the audit requirement.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/governance/policy/concepts/exemption-structure

### Q-AZ104-011 · Manage Azure identities and governance · difficulty 3 · scenario

A `Modify` policy must set `allowSharedKeyAccess: false` on existing storage accounts. After assignment, compliance shows the accounts as non-compliant but nothing changes; the assignment uses a system-assigned identity with `Reader` on the subscription. What is missing?

- A) The initiative must also contain an `Append` effect for the same property.
- B) A remediation task must be created, and the assignment identity needs a role that can write the resource, such as `Contributor` or a custom role with `Microsoft.Storage/storageAccounts/write`.
- C) The assignment must switch to `enforcementMode: DoNotEnforce` before `Modify` applies to existing resources.
- D) Storage account shared key access cannot be changed by policy.

<details><summary>Answer</summary>

**B.** `Modify` is a request-time effect, so existing resources need an explicit remediation task, and that task acts as the assignment's managed identity. `Reader` can evaluate compliance but cannot PATCH the account, which is why the compliance state changed and the resource did not.

- Why not A: `Append` is a separate request-time effect and would not repair existing resources either.
- Why not C: `DoNotEnforce` disables the effect rather than enabling retroactive repair.
- Why not D: the property is a normal ARM property, which is why both `Modify` and a `Deny` on the same path work.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/governance/policy/concepts/effect-modify

### Q-AZ104-012 · Manage Azure identities and governance · difficulty 2 · multi

Which two controls protect blob data from deletion by a principal that holds `Owner` on the storage account? (Choose two.)

- A) A `CanNotDelete` lock on the storage account.
- B) Blob soft delete with a retention window, combined with blob versioning.
- C) A `ReadOnly` lock on the storage account.
- D) A time-based immutability policy on the containers that hold regulated data.

<details><summary>Answer</summary>

**B, D.** Locks are ARM control-plane objects, so a principal with a data-plane role deletes blobs without ever touching them. Data protection therefore needs data-plane controls: soft delete plus versioning gives recovery, and a time-based immutability policy makes objects unmodifiable and undeletable for the retention period even for an account owner.

- Why not A: `CanNotDelete` prevents deleting the account object, not the blobs inside it.
- Why not C: `ReadOnly` freezes the configuration while leaving blob writes and deletes available to a data role.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), [modules/07-storage-blob-files-and-data-protection.md](../modules/07-storage-blob-files-and-data-protection.md), https://learn.microsoft.com/en-us/azure/storage/blobs/immutable-storage-overview

</details>

### Q-AZ104-013 · Manage Azure identities and governance · difficulty 3 · single

A user assigned a custom role with `Actions: ["*"]` and `NotActions: ["Microsoft.Storage/storageAccounts/delete"]` deletes a storage account, because they also hold the built-in `Contributor` role. Why did the delete succeed?

- A) `NotActions` is ignored whenever `Actions` is the wildcard.
- B) The exclusion should have been expressed with `NotDataActions` instead.
- C) `NotActions` only subtracts from that role's own allowed actions; `Contributor` grants the delete independently, so the union permits it, and blocking it requires a deny assignment or a `DenyAction` policy.

- Why not B: `NotDataActions` applies to data actions, not control-plane deletes.
- Why not D: `AssignableScopes` governs where a definition can be assigned, not whether an assigned role applies.

### Q-AZ104-014 · Manage Azure identities and governance · difficulty 3 · ordering

You must roll out a new `Deny` policy that requires private endpoints for storage accounts across 60 subscriptions without causing an outage. Place the steps in the correct order.

- A) Assign with `enforcementMode: DoNotEnforce`, review compliance and `what-if` output on a pilot, confirm pilot workloads already satisfy the rule, then switch to `Default` and widen the scope.
- B) Switch every subscription to `Default`, review compliance, create exemptions for every failure, then assign remediation.
- C) Create exemptions for every subscription first, assign with `Default`, run `what-if`, then switch to `DoNotEnforce`.
- D) Assign at the tenant root with `Default`, disable the storage firewall, deploy private endpoints, then remove the locks.

<details><summary>Answer</summary>

**A.** Audit mode computes compliance without blocking, `what-if` previews the resource changes a deployment would make, and only a proven pilot justifies enforcement. This ordering produces the blast-radius evidence before any request is rejected.

- Why not B: enforcing first is the outage, and no remediation can repair a request that `Deny` already rejected.
- Why not C: exemptions granted before evidence disable the control without knowledge of the impact, and the mode sequence is inverted.
- Why not D: tenant-root enforcement plus disabling the firewall inverts the security requirement.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/governance/policy/concepts/assignment-structure

### Q-AZ104-018 · Implement and manage storage · difficulty 3 · scenario

After a customer-initiated failover of a GRS storage account, the account reports LRS and the team assumes regional protection is intact. What actually happened, and what must be done?

- A) The account is now RA-GRS, because geo-replication resumed automatically in the reverse direction.
- B) Failover promoted the secondary and re-pointed the account CNAME; geo-replication is directional, so the account was converted to LRS and must be explicitly reconfigured to GRS or GZRS, which reseeds a new secondary.
- C) The account remains GRS, but the original region's copy is read-only until that region returns.
- D) Failover created a new account in the secondary region and the failed-over account must be deleted.

- Why not A: no automatic reverse replication exists; the redundancy property must be changed deliberately.
- Why not C: the account is not geo-redundant after failover, which is the dangerous part because dashboards still say GRS.
- Why not D: the same account object is retained, which is why clients must re-resolve DNS.

### Q-AZ104-019 · Implement and manage storage · difficulty 2 · scenario

An auditor requests 400 archived blobs totalling 2 TB, and compliance wants them readable within four hours. What must you tell them?

- A) A lifecycle rule can restore the blobs to the Hot tier automatically within minutes.
- B) Archived blobs can be read directly with higher latency and a retrieval charge.
- C) Deleting and re-uploading the blobs is faster because Archive has no rehydration queue.
- D) Archive is offline: each blob must be rehydrated, standard rehydration takes hours and high priority is typically under an hour per blob but the account is capped near 10 GiB per hour, so 2 TB cannot be ready in four hours and the request must be prioritised or copied in stages.

### Q-AZ104-062 · Monitor and maintain Azure resources · difficulty 2 · scenario

During a planned migration, 400 alerts flood the on-call channel, but the same alerts must still fire and be recorded. What should you configure?

- A) Disable the alert rules for the duration and re-enable them afterwards.
- B) An alert processing rule scoped to the affected resources with a schedule that suppresses notifications, or routes them to a maintenance action group, while the alerts still fire and are recorded.
- C) Delete the action group so no notifications are sent.
- D) Raise the severity of every rule so the on-call engineer can triage faster.

<details><summary>Answer</summary>

**B.** An alert processing rule can add or suppress action groups on fired alerts, optionally on a schedule. Suppression removes the notification noise while leaving the rule evaluation and alert history intact, which is exactly the requirement.

- Why not A: disabled rules produce no alert history, so the record is lost.
- Why not C: deleting the action group breaks every other alert that uses it.
- Why not D: severity does not reduce volume.
- Ref: [modules/09-security-monitoring-and-bcdr.md](../modules/09-security-monitoring-and-bcdr.md), https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-processing-rules

</details>

### Q-AZ104-063 · Monitor and maintain Azure resources · difficulty 1 · single

Which Network Watcher capability identifies the NSG rule that allows or denies a specific five-tuple flow to a VM?

- A) Connection troubleshoot
- B) Next hop
- C) Packet capture
- D) IP flow verify

<details><summary>Answer</summary>

**D.** IP flow verify evaluates a five-tuple against the effective NSG rules on the NIC and subnet and returns the decision together with the name of the rule that produced it.

- Why not A: connection troubleshoot tests end-to-end reachability and reports where it fails, without naming the deciding NSG rule.
- Why not B: next hop reports the routing decision for a destination address.
- Why not C: packet capture records traffic for offline analysis.
- Ref: [modules/04-virtual-networking-private-link-and-routing.md](../modules/04-virtual-networking-private-link-and-routing.md), https://learn.microsoft.com/en-us/azure/network-watcher/ip-flow-verify-overview

</details>

### Q-AZ104-064 · Monitor and maintain Azure resources · difficulty 3 · multi

Which two statements about validating an Azure Site Recovery recovery plan are correct? (Choose two.)

- A) A test failover creates VMs in an isolated network without affecting production replication, and the compute consumed during the drill is billed.
- B) A test failover permanently stops replication and requires re-protection afterwards.
- C) Crash-consistent recovery points are generated every five minutes and that frequency is fixed, while application-consistent points require VSS or a custom freeze-thaw and have a minimum one-hour frequency.
- D) Recovery plans cannot contain scripts or manual steps.

<details><summary>Answer</summary>

**A, C.** A test failover is the only safe way to prove a recovery plan: it builds the VMs in an isolated network, leaves replication running, and bills only the compute it creates. The two recovery-point classes have different mechanics and different minimum intervals.

- Why not B: replication continues during a test failover; re-protection is a real-failover concern.
- Why not D: scripts, manual pauses, and dependency ordering are the main value of a recovery plan.
- Ref: [modules/09-security-monitoring-and-bcdr.md](../modules/09-security-monitoring-and-bcdr.md), https://learn.microsoft.com/en-us/azure/site-recovery/site-recovery-test-failover-to-azure

</details>

### Q-AZ104-065 · Monitor and maintain Azure resources · difficulty 3 · scenario

A ransomware incident encrypted backups in a Recovery Services vault. The security team wants future recovery points to be undeletable even by a subscription `Contributor`. What must be configured, and what is the risk?

- A) A `CanNotDelete` lock on the vault, which also prevents deletion of backup data.
- B) An immutable vault with a locked immutability policy and soft delete enabled; once the policy is locked it cannot be removed or shortened, so retention mistakes become irreversible for the configured duration.
- C) Azure Site Recovery with a recovery plan, which makes recovery points immutable.
- D) A `ReadOnly` lock on the vault, which prevents data-plane deletion.

<details><summary>Answer</summary>

**B.** An immutable vault blocks operations that would remove recovery points, and locking the policy makes that guarantee resistant to an administrator who later wants to weaken it. The same property is the risk: a wrong retention value becomes a multi-month or multi-year commitment that cannot be undone.

- Why not A: a lock is an ARM object that an `Owner` can remove, and it does not make recovery points immutable.
- Why not C: Site Recovery orchestrates failover and does not create immutable backups.
- Why not D: `ReadOnly` locks are removable and do not govern data-plane deletion.
- Ref: [modules/09-security-monitoring-and-bcdr.md](../modules/09-security-monitoring-and-bcdr.md), https://learn.microsoft.com/en-us/azure/backup/backup-azure-immutable-vault-concept

</details>
