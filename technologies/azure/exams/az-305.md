### Q-AZ305-001 · Design identity, governance, and monitoring solutions · difficulty 2 · scenario

Contoso must organize 400 subscriptions split across Platform and Landing Zones, and a proposal nests eight management group levels to model region, business unit, and team. Which design should the architect recommend?

- A) Accept eight levels, because management groups support unlimited nesting and Azure Policy inheritance works at every depth.
- B) Limit the hierarchy to six levels below the root, and express finer granularity with tags and subscription-scoped RBAC.
- C) Replace management groups with tagged resource groups, because Azure Policy inherits from resource groups by tag value.
- D) Create one management group per subscription and assign policies individually to each subscription.

<details><summary>Answer</summary>

**B.** Management group hierarchies support up to six levels of depth, excluding the root and subscription levels, so an eight-level design fails at deployment. Policy inheritance follows the management group hierarchy, not tags, and tags and subscription-scoped RBAC handle the finer grain.

- Why not A: The hierarchy is capped at six levels, so the proposal cannot be deployed as written.
- Why not C: Azure Policy inherits by scope (management group, subscription, resource group), and tags only filter policy conditions.
- Why not D: One management group per subscription adds no inheritance and multiplies assignments without reducing drift.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/governance/management-groups/overview

</details>

### Q-AZ305-002 · Design identity, governance, and monitoring solutions · difficulty 3 · scenario

A production network stack is deployed by a deployment stack and must not be deleted by anyone, including subscription Owners, except a named break-glass group that must still be able to remove it during an incident. Which mechanism enforces this at the platform level?

- A) An Azure Policy deny effect that blocks delete operations on all resources in the resource group.
- B) A deployment stack with denySettings mode denyDelete and the break-glass group listed in excludedPrincipals.
- C) A CanNotDelete resource lock on the resource group, with the break-glass group granted the Owner role.
- D) An Azure Blueprints assignment with a locked artifact set and Contributor rights for operators.

<details><summary>Answer</summary>

**B.** Deny settings are enforced by Azure Resource Manager on requests against resources in the stack, and excludedPrincipals exempts only the listed identities. The deny applies to subscription Owners as well, which is the requirement.

- Why not A: Azure Policy deny evaluates most create and update requests and does not reliably block deletes of arbitrary resources.
- Why not C: Any principal with Owner rights can remove a resource lock, so the lock cannot hold against subscription Owners.
- Why not D: Blueprints are the legacy model that Microsoft recommends replacing with deployment stacks, and they do not provide per-principal exclusions.
- Ref: [modules/01-tenancy-governance-and-policy.md](../modules/01-tenancy-governance-and-policy.md), https://learn.microsoft.com/en-us/azure/azure-resource-manager/bicep/deployment-stacks

</details>

### Q-AZ305-003 · Design identity, governance, and monitoring solutions · difficulty 2 · ordering

Order the steps that let a GitHub Actions workflow deploy to Azure without any stored client secret.

- A) The workflow requests an access token from Azure Resource Manager directly; Entra ID validates the RBAC role; the workflow then receives a GitHub OIDC token.
- B) GitHub issues an OIDC token for the run; the workflow presents it to Entra ID; Entra ID validates the issuer and subject against the federated credential and issues an access token; Resource Manager authorizes the request against the role assignment.
- C) Entra ID issues an access token; GitHub issues an OIDC token; Resource Manager authorizes the request; the workflow presents the token to Entra ID for validation.
- D) The workflow reads a client secret from GitHub secrets; Entra ID issues an access token; Resource Manager checks the subject claim before authorizing.

<details><summary>Answer</summary>

**B.** Workload identity federation starts with GitHub minting an OIDC token for the workflow run. Entra ID trusts that token only after it matches the federated credential's issuer and subject, and Resource Manager then evaluates RBAC on the resulting access token.

- Why not A: RBAC is evaluated by Resource Manager after Entra ID issues a token, and the OIDC token must exist before any exchange.
- Why not C: Entra ID cannot issue a token before it validates the presented OIDC token.
- Why not D: The sequence describes a stored-secret flow, which the requirement forbids, and Resource Manager does not check the subject claim.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/entra/workload-id/workload-identity-federation

</details>

### Q-AZ305-004 · Design identity, governance, and monitoring solutions · difficulty 3 · scenario

A regulated bank must remove standing Owner access on its landing zone management groups, yet platform engineers still need Owner for incident response within a bounded window with an audit trail. Which design best satisfies these constraints?

- A) Keep permanent Owner for a security group and add a Conditional Access policy that requires MFA at sign-in.
- B) Assign Owner as an eligible role in Privileged Identity Management, with MFA and approval required on activation and a time-bound activation duration.
- C) Share a single break-glass Owner account whose password is stored in a vault and rotated monthly.
- D) Create a custom role without role-assignment write permissions and assign it permanently to the platform group.

<details><summary>Answer</summary>

**B.** Privileged Identity Management converts standing access into eligible access. Activation is just-in-time, can require MFA and approval, lasts a bounded time, and produces audit records. Eligible assignments require Entra ID P2 or Entra ID Governance licensing.

- Why not A: MFA at sign-in does not remove standing privilege, which is the actual requirement.
- Why not C: A shared account has no per-person attribution, and it is an emergency-access mechanism, not a daily activation path.
- Why not D: A custom role still grants standing permissions and offers no just-in-time activation.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/entra/id-governance/privileged-identity-management/pim-configure

</details>

### Q-AZ305-005 · Design identity, governance, and monitoring solutions · difficulty 1 · single

Which statement about managed identities in Microsoft Entra ID is correct?

- A) A system-assigned managed identity can be shared by several resources, and it survives deletion of its host resource.
- B) A user-assigned managed identity is deleted automatically when the last resource that uses it is removed.
- C) A user-assigned managed identity is a standalone resource that several Azure resources can share, with a lifecycle independent of them.
- D) Managed identities require a client secret that the platform rotates every 90 days.

<details><summary>Answer</summary>

**C.** A user-assigned managed identity is its own resource. Several Azure resources can reference it, and it persists until someone deletes it explicitly.

- Why not A: A system-assigned identity is bound one-to-one to its resource and is deleted with it.
- Why not B: User-assigned identities are not garbage-collected when their consumers are removed.
- Why not D: Managed identities have no secret that the customer manages or handles.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview

### Q-AZ305-006 · Design identity, governance, and monitoring solutions · difficulty 3 · single

A storage account holds blobs for many projects. A data scientist must read only blobs tagged `Project=Alpha`, using Entra ID and no SAS tokens. Which configuration achieves this?

- A) Assign Storage Blob Data Reader at the account scope with a role assignment condition that matches the blob index tag `Project` to `Alpha`.
- B) Create a custom role with blob read permissions and assign it at the container scope.
- C) Assign Storage Blob Data Reader at the container scope and rely on an `alpha/` name prefix for the blobs.

<details><summary>Answer</summary>

**A.** Attribute-based access control conditions on Azure Storage can evaluate blob index tags, so one role assignment is narrowed by an attribute rather than by container or name. This keeps authorization in Entra ID.

- Why not B: A custom role can narrow by action and scope, but it cannot filter individual blobs by tag.
- Why not C: Name prefixes are not an enforced attribute, and the container-scope grant still covers every blob in it.
- Why not D: Stored access policies govern SAS tokens, which the requirement excludes.
- Ref: [modules/02-entra-id-rbac-and-workload-identity.md](../modules/02-entra-id-rbac-and-workload-identity.md), https://learn.microsoft.com/en-us/azure/role-based-access-control/conditions-overview

### Q-AZ305-007 · Design identity, governance, and monitoring solutions · difficulty 2 · scenario

A company ingests 2 TB per day of verbose firewall and proxy logs into a Log Analytics workspace. Analysts query those logs only during investigations, and compliance requires seven years of retention. Which approach minimizes cost while meeting these needs?

- A) Keep all logs in the Analytics tier with a seven-year workspace retention setting.
- B) Export all logs to Event Hubs and discard them after ingestion.
- C) Move the logs to a storage account with lifecycle rules and query them only through Power BI.

- Why not A: Analytics-tier ingestion and retention cost scale with volume, which the rarely queried logs do not justify.
- Why not B: Discarding the logs violates the seven-year retention requirement.
- Why not C: Storage removes KQL investigation from the same workspace and splits the audit trail across two systems.

### Q-AZ305-008 · Design identity, governance, and monitoring solutions · difficulty 3 · scenario

Thirty subscriptions must send VM performance counters and event logs to one central workspace through a single data collection rule (DCR), and new VMs must be onboarded automatically without a pipeline change. Which mechanism meets this requirement?

- A) An Azure Policy assignment at the management group that uses DeployIfNotExists to create the DCR association on every VM.
- B) A scheduled Logic App that runs hourly and attaches the DCR to any VM that lacks an association.

- Why not C: Manual associations drift and do not onboard new VMs automatically.
- Why not D: Tags do not create DCR associations, and the agent needs the association to send data.
