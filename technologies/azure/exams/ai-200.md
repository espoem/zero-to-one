### Q-AI200-001 · Develop containerized solutions on Azure · difficulty 2 · scenario

A team must run an AI inference API on Azure Container Apps. The API receives steady traffic around the clock at a predictable rate, and each replica needs 4 vCPU and 8 GB of memory. The team wants predictable latency and a fixed monthly compute cost rather than per-second billing. Which environment type fits?

- A) Create a Consumption-only environment, set `minReplicas` to 10, and rely on HTTP-concurrency KEDA rules to absorb the load.
- B) Create a Workload Profiles environment, define a dedicated workload profile sized at 4 vCPU and 8 GB, and pin the app to that profile.
- C) Create a Consumption environment and raise `maxReplicas` to 40 so KEDA always has headroom.
- D) Deploy the same container to Azure Container Instances as a group of 10 instances behind Azure Front Door.

<details><summary>Answer</summary>

**B.** The Consumption profile is serverless: it bills the vCPU-seconds and memory-seconds that replicas actually consume and scales to zero when idle. A steady 24/7 workload with a hard per-replica CPU and memory requirement is exactly the case the Dedicated workload profile exists for: the environment reserves a fixed pool of compute with defined vCPU and memory sizes, the cost is the reserved capacity rather than per-replica seconds, and the profile guarantees the CPU and memory envelope the inference runtime needs.

- Why not A: `minReplicas` of 10 on Consumption still bills per second for every running replica, and the Consumption envelope does not give the app the 4 vCPU and 8 GB per-replica shape that the inference runtime requires.
- Why not C: `maxReplicas` only sets a ceiling. It reserves nothing, does not change the billing model, and does not give the app the per-replica vCPU and memory it needs.
- Why not D: Container Instances groups have no autoscaling engine and no managed ingress routing layer, so Front Door in front of fixed groups adds routing without adding revisions, rollouts, or scaling.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/overview

</details>

### Q-AI200-002 · Develop containerized solutions on Azure · difficulty 2 · scenario

A Container Apps worker consumes an Azure Service Bus queue through a KEDA `azure-servicebus` scale rule configured with `messageCount: 50`, `minReplicas: 0`, and `maxReplicas: 20`. At 09:00 the queue's active message count is 600 and no replica is currently running. How many replicas does KEDA target?

- A) 12, because the target replica count is the active message count divided by the threshold, clamped to the configured minimum and maximum.
- B) 20, because a queue trigger scales to the maximum replica count whenever the queue is non-empty.
- C) 1, because a queue trigger admits exactly one replica per queue regardless of depth.
- D) 0, because scale-to-zero applies whenever any scale rule's metric is non-zero.

<details><summary>Answer</summary>

**A.** KEDA converts the trigger's metric into a desired replica count by dividing the current metric by the threshold and rounding up, then clamps the result to the range between `minReplicas` and `maxReplicas`. With 600 active messages and a threshold of 50, the target is 12 replicas, which sits inside the 0-to-20 range, so KEDA scales up to 12. The threshold is therefore a throughput decision expressed as backlog per replica, and it is the number to tune against the handler's real service time.

- Why not B: The trigger metric and threshold produce the target; `maxReplicas` is only the upper clamp applied to that result.
- Why not C: Nothing in the Service Bus scale rule limits a queue trigger to a single replica; the metric is the queue depth, not a boolean.
- Why not D: Scale-to-zero is the behaviour when the metric is zero, not when it is large; a non-zero backlog is precisely the case that produces replicas.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/scale-app

</details>

### Q-AI200-003 · Develop containerized solutions on Azure · difficulty 3 · scenario

A Container Apps consumer reads from an Azure Event Hubs instance with four partitions. The KEDA `azure-eventhub` rule scales on per-partition lag with a threshold of 100 events, `minReplicas: 0`, and `maxReplicas: 40`. The team has hit the maximum read throughput the service allows for its consumer group and wants to double the read parallelism. Which change achieves that?

- A) Set `maxReplicas` to 40 and keep the threshold at 100, because the plateau is caused by the replica ceiling.
- B) Lower the threshold to 10, because a smaller threshold makes KEDA add a reader to each partition.
- C) Increase the partition count on the Event Hubs instance so more partitions are available, and plan for the fact that changing the partition count changes how producer keys map to partitions.
- D) Enable Event Hubs Capture so that a second consumer can read the captured files in parallel.

<details><summary>Answer</summary>

**C.** Within one consumer group, at most one reader is active per partition, so the read parallelism of a group is capped by the partition count no matter how high `maxReplicas` is. Adding partitions is the only way to add in-band reader parallelism, and it is a design-time decision because changing the partition count later changes how producer keys map to partitions, so any key-affinity assumption has to be revisited and the existing data redistributed or re-keyed.

- Why not A: Raising `maxReplicas` adds replicas that compete for the same four partitions; the group still admits one reader per partition, so throughput does not rise.
- Why not B: A lower threshold raises the target replica count, but those replicas still contend for the same four partitions, so the group reads no faster and the extra replicas only cost money.
- Why not D: Capture writes the stream to Blob Storage or Data Lake in Avro files. It is an archival path for a different consumer, not a way to add reader parallelism to the live stream.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/scale-app

</details>

### Q-AI200-004 · Develop containerized solutions on Azure · difficulty 1 · single

A Container Apps HTTP API serves an interactive chat assistant. The service-level objective sets a p95 first-byte latency of 400 ms, and the traffic is bursty, with minutes of activity followed by hours of idle. The app runs with `minReplicas: 0` and an HTTP-concurrency KEDA rule. Which change best protects the latency objective?

- A) Keep `minReplicas: 0` and add a second HTTP-concurrency rule with a lower threshold.
- B) Set `minReplicas: 1` so at least one warm replica absorbs the first request of a burst while the rest scale out.
- C) Increase `maxReplicas` to 50 so the burst is absorbed by newly started replicas.
- D) Change the ingress transport to HTTP/2 automatic.

<details><summary>Answer</summary>

**B.** Scale-to-zero is a latency trade. A replica that was removed must be re-created, must pull or reuse its image, must run its start-up code, and must establish its connections before it serves the first request. Keeping one always-warm replica removes that cold start from the user-facing path, while the HTTP-concurrency rule still handles the burst above the floor. The alternative is to accept a measured cold-start penalty and write it into the service-level objective.

- Why not A: A second rule with a lower threshold makes KEDA add replicas sooner, which helps the ramp after a replica exists but does nothing about the cold start of the very first request.
- Why not C: A higher maximum means more replicas are available during a burst, but every one of them is a cold start, so the p95 of the first requests after an idle period gets worse rather than better.
- Why not D: The ingress transport affects connection handling at the edge; it does not shorten the replica start-up path inside the platform.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/scale-app

</details>

### Q-AI200-005 · Develop containerized solutions on Azure · difficulty 3 · scenario

A team runs a Container Apps inference service in single revision mode. A new revision with a changed model version is deployed, and 40 seconds later the p95 latency and error rate jump. The team must roll back without redeploying and keep the failed revision available for debugging. Which configuration change enables this?

- A) Switch the app to multiple revision mode, deploy the new revision with zero traffic weight, and move 100 percent of the traffic weight back to the previous revision.
- B) Keep single revision mode and redeploy the previous image tag, because in single mode the previous revision is deactivated as soon as the new one becomes active.
- C) Enable `allowInsecure` on the ingress and route internal testers to the failed revision by hostname.
- D) Set `minReplicas` to 0 on the new revision so the failed revision is discarded automatically.

<details><summary>Answer</summary>

**A.** A revision is an immutable snapshot of an app's template, covering image, environment variables, scale rules, and resource limits, so any change to those creates a new revision. In single revision mode the newest ready revision replaces the previous one and the old one is deactivated, which leaves no traffic weight to move and no revision left to roll back to. Multiple revision mode keeps several revisions active at once with explicit traffic weights, which turns rollback into a weight change rather than a redeploy and leaves the failed revision addressable at zero weight for inspection.

- Why not B: In single revision mode the previous revision is deactivated when the new one activates, so the only route back is to redeploy the old template, which is exactly the redeploy the requirement rules out.
- Why not C: `allowInsecure` relaxes TLS behaviour at the ingress. It does not create a routable path to an individual revision and it does not restore a rollback target.
- Why not D: `minReplicas` of 0 only lets the failed revision scale to zero. The revision itself stays active and addressable, and scaling it down is not a rollback.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/revisions

</details>

### Q-AI200-006 · Develop containerized solutions on Azure · difficulty 2 · scenario

A team has shifted 20 percent of production traffic to revision `v2` of a Container App. A tester must exercise `v2` directly against production-scale payloads, including the cases that the canary weighting makes rare. Which mechanism gives the tester a stable URL that reaches `v2` only?

- A) A revision label assigned to `v2`, which produces a dedicated hostname for that revision.
- B) The `prod` label reassigned to `v2`, which moves all labelled traffic to the candidate.
- C) A query string on the shared environment URL that selects the revision.
- D) A Dapr service invocation binding scoped to the revision.

<details><summary>Answer</summary>

**A.** A revision label gives a stable hostname to one specific revision, so the tester reaches the candidate through the label URL while production traffic continues to follow the ingress weights. Labels are independent of the weight split, which is exactly what lets a canary and a direct test coexist against the same deployment.

- Why not B: Reassigning the `prod` label moves all traffic that resolves that label, which is the opposite of keeping production on the stable revision, and it loses the stable label for the revision that should keep it.
- Why not C: The environment ingress URL routes by traffic weight. There is no query-string revision selector on the shared hostname.
- Why not D: Dapr service invocation is an in-cluster calling convention for an application's own dependencies; it does not publish a revision-scoped public hostname.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/revisions

</details>

### Q-AI200-007 · Develop containerized solutions on Azure · difficulty 2 · multi

A team runs three Container Apps that must exchange state and events without taking a direct dependency on a specific broker SDK. Which statements about adopting the Dapr sidecar are correct? (Select all that apply.)

- A) Dapr exposes building blocks such as state management, publish and subscribe, and service invocation over a local HTTP or gRPC endpoint that the application calls.
- B) The Dapr pub/sub building block delivers at-least-once semantics, so every subscriber handler must be idempotent.
- C) Enabling Dapr adds a second process to every replica and an extra network hop on each call, so the abstraction has a measurable runtime cost.
- D) Dapr sidecars automatically translate the Azure Service Bus peek-lock state machine into exactly-once delivery, removing the need for idempotent handlers.

<details><summary>Answer</summary>

**A, B, C.** Dapr is worth using when the application should depend on an abstract capability such as "save state" or "publish an event" rather than on a specific broker SDK, and when the sidecar should own retries and mutual TLS between services. It is not free: each sidecar adds a process to every replica, a second hop on each call, and a configuration surface covering components, scopes, and resiliency policies that must be versioned like code.

- Why not D: The pub/sub building block inherits the delivery guarantee of the broker underneath it. Azure Service Bus is an at-least-once broker, so a redelivery after a lost lock is still possible and the sidecar does not upgrade it to exactly-once.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/dapr-overview

</details>

### Q-AI200-008 · Develop containerized solutions on Azure · difficulty 2 · scenario

A team must embed a corpus of 200,000 documents into vectors as a one-off backfill. Each document takes about 30 seconds to embed, the work items arrive on an Azure Service Bus queue, and the job must never run more than 40 containers at once. Which Container Apps Job configuration fits?

- A) A scheduled job with a cron expression of `*/5 * * * *` and `maxReplicas: 40`.
- B) An event-driven job with the queue as the KEDA source, `maxReplicas: 40`, an explicit replica timeout, and an explicit retry limit.
- C) A manual job with `maxReplicas: 40` and no retry configuration.
- D) A manual job that polls the queue with a timer and downloads the whole queue on start.

<details><summary>Answer</summary>

**B.** An event-driven Container Apps Job starts a replica per unit of work in a KEDA source and runs until the work is consumed, which turns a queue into a parallel batch and lets the platform own the fan-out. The replica timeout and the retry limit must be set explicitly: a job that exceeds its timeout is stopped, and a job that retries without idempotency repeats its side effects, so the same idempotency rule that applies to a queue handler applies to the job.

- Why not A: A scheduled job runs the container on a cron schedule. It does not consume the queue, so the container would have to drain the queue itself and the per-item parallelism would be lost.
- Why not C: A manual job runs to completion once when triggered. Without an explicit retry limit the failure behaviour is undefined, and a single invocation gives no per-item concurrency.
- Why not D: Draining the whole queue into one job holds every message at once, loses the per-item scaling model, and a crash restarts the entire backfill from the beginning.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/jobs

</details>

### Q-AI200-009 · Develop containerized solutions on Azure · difficulty 1 · single

A CI pipeline deploys a Container App that pulls its image from a private Azure Container Registry. The team wants to remove the registry admin password from the deployment. What is the minimum change?

- A) Assign the `AcrPull` role to the Container App's managed identity at the registry scope.
- B) Assign the `AcrPush` role to the Container App's managed identity.
- C) Store the registry admin password in a Key Vault secret and reference it from the app.
- D) Set the registry's `anonymousPullEnabled` to true and remove the image reference secret.

<details><summary>Answer</summary>

**A.** `AcrPull` grants pull-only access to the registry's repositories and is the least-privilege role for a workload that only consumes images. Assigning it to the app's managed identity removes the credential entirely: the platform obtains an Entra ID token and authenticates to the registry with it, so nothing secret is stored in the pipeline or in the app configuration.

- Why not B: `AcrPush` grants push and pull. A consuming workload does not need push, and granting it widens the blast radius of a compromised workload identity.
- Why not C: Moving the admin password into Key Vault still leaves a long-lived shared credential with account-wide rights, including the ability to delete every repository. It hides the secret rather than removing it.
- Why not D: Enabling anonymous pull publishes every repository in the registry to anyone who can reach it, which converts a private image supply chain into an unauthenticated one.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-registry/container-registry-rbac-built-in-roles-overview

</details>

### Q-AI200-010 · Develop containerized solutions on Azure · difficulty 3 · scenario

A regulated platform team uses an Azure Container Registry with ABAC-enabled repository permissions. A Container App pulls images from it using a system-assigned managed identity. Which role assignment gives that identity pull access without granting it rights over other repositories in the registry?

- A) `AcrPull` at the registry scope.
- B) `Container Registry Repository Reader` scoped to the specific repository.
- C) `Contributor` at the resource group that contains the registry.
- D) `AcrPush` scoped to the specific repository.

<details><summary>Answer</summary>

**B.** On an ABAC-enabled registry the repository-scoped roles are the mechanism for narrow pull grants, so `Container Registry Repository Reader` scoped to one repository names exactly the artefact the app consumes and nothing else. `AcrPull` remains the pull role for registries that are not ABAC-enabled, and at registry scope it grants pull across every repository in that registry.

- Why not A: On an ABAC-enabled registry the repository-scoped roles are the intended shape; a registry-scope `AcrPull` assignment is the blanket grant and does not express the per-repository boundary the platform team requires.
- Why not C: `Contributor` is a control-plane role that permits managing the registry resource itself, including deleting it, and it confers no data-plane pull permission at all.
- Why not D: `AcrPush` grants push as well as pull and is the wrong direction for a consuming workload.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-registry/container-registry-rbac-built-in-roles-overview

</details>

### Q-AI200-011 · Develop containerized solutions on Azure · difficulty 3 · scenario

A team is enabling Microsoft Entra Workload ID on an AKS Standard cluster so that its pods can call Azure APIs with an Azure-managed identity instead of a stored client secret. Which set of changes is required?

- A) Inject a credential into each pod's environment variable and set `usePodIdentity` in the Secrets Store CSI driver.
- B) Enable workload identity and the OIDC issuer on the cluster, annotate the Kubernetes service account with the client ID, create a federated identity credential for the service account subject, and label the pod `azure.workload.identity/use: "true"`.
- C) Assign `AcrPull` to the AKS cluster's system-assigned identity and remove the OIDC issuer.
- D) Create an Entra app registration with a client secret, store the secret through the Key Vault CSI driver, and mount it into the pods.

<details><summary>Answer</summary>

**B.** Workload ID federates the cluster's OIDC issuer with Entra ID so that a projected service account token can be exchanged for an Azure access token. That requires the cluster to publish an OIDC issuer, the service account to be annotated with `azure.workload.identity/client-id`, a federated identity credential whose subject is `system:serviceaccount:<namespace>:<serviceaccount>`, and the pod to carry the `azure.workload.identity/use: "true"` label so the mutating webhook injects the projected token volume and the `AZURE_FEDERATED_TOKEN_FILE` variable. A mismatch in the issuer, namespace, or service account name produces a token-exchange error that does not say which field is wrong.

- Why not A: A credential in an environment variable is a stored secret, which is exactly the model workload identity removes. `usePodIdentity` refers to the retired Entra pod-managed identity project, not to workload identity.
- Why not C: `AcrPull` on the cluster's identity covers image pulls by the kubelet. It says nothing about how a pod authenticates to other Azure services, and removing the OIDC issuer removes the token the federation depends on.
- Why not D: A client secret mounted from Key Vault is the pattern workload identity is meant to replace; it keeps the long-lived credential and its rotation burden in the cluster.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/aks/workload-identity-overview

</details>

### Q-AI200-012 · Develop containerized solutions on Azure · difficulty 2 · scenario

A team wants to build a container image and push it to Azure Container Registry from a repository that has no local Docker daemon and no CI runner with a Docker socket. Which mechanism performs the build?

- A) An Azure Container Registry Task, which builds the image inside the registry from a Dockerfile in the source repository.
- B) Azure Container Instances with a container group that runs `docker build` against the registry.

### Q-AI200-013 · Develop containerized solutions on Azure · difficulty 3 · scenario

A platform team hosts forty internal APIs and three event consumers on Kubernetes. The APIs need rolling deployment, traffic splitting, and per-service autoscaling, but the team has no Kubernetes administrators and no budget for a node-pool operating model. Which Azure service fits best, and what trade-off does the team accept?

- A) Azure Kubernetes Service, because only AKS provides traffic splitting.
- B) Azure Container Apps, which provides revisions, traffic weights, and KEDA scaling without a cluster to administer, at the cost of giving up the Kubernetes API, custom controllers, and per-pod scheduling control.
- C) Azure App Service plans, because each app can be deployed as a container and autoscales per plan instance.
- D) Azure Container Instances groups behind Azure Front Door, because container groups autoscale automatically.

<details><summary>Answer</summary>

**B.** Container Apps provides exactly the capabilities the team listed, namely immutable revisions, ingress traffic weights for canary and blue-green rollouts, and KEDA-driven scaling including scale to zero, while removing the node-pool operating surface. The trade-off is the Kubernetes API itself: custom operators, arbitrary scheduling directives, and per-pod resource control are not available, so a platform that other teams need to extend with controllers is the case that argues for AKS instead.

- Why not A: AKS does provide traffic splitting through an ingress controller, but it requires the team to own cluster upgrades, node pools, ingress controllers, and the Kubernetes API, which is precisely the operating model the team said it has no budget for.
- Why not C: App Service scales a whole plan instance rather than individual apps, so forty independent services share one scaling unit, and deployment slots are an App Service rollout mechanism rather than the revision model.
- Why not D: Container Instances groups have no autoscaling engine, so every scale decision is manual or scripted, and Front Door adds routing without adding revisions.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/overview

</details>

### Q-AI200-014 · Develop containerized solutions on Azure · difficulty 2 · multi

A Container Apps environment hosts three apps with different trust levels: a public-facing API, an internal scoring service, and a data-ingest worker. Which configurations are correct? (Select all that apply.)

- A) Expose only the public API with external ingress and keep the internal services on internal ingress.
- B) Enable mutual TLS at the environment level so traffic between apps inside the environment is encrypted with certificates.
- C) Use Entra ID authentication on the external ingress to decide who the caller is, separately from the transport encryption that mutual TLS provides.
- D) Enable environment-level mutual TLS and then delete the ingress certificates, because the sidecars reissue them for every app.

<details><summary>Answer</summary>

**A, B, C.** Authentication and transport encryption are separate concerns: Entra ID authentication on the ingress answers who the caller is, and environment-level mutual TLS answers who can read the bytes between apps. Keeping the internal services on internal ingress removes them from the public edge entirely, and enabling mutual TLS protects a neighbour's traffic from a compromised app on the same environment network.

- Why not D: Environment-level mutual TLS issues and rotates certificates for traffic between apps. The ingress certificates for external traffic are managed separately, and deleting them breaks external ingress rather than delegating it to the sidecars.
- Ref: [modules/05-compute-vms-app-service-and-containers.md](../modules/05-compute-vms-app-service-and-containers.md), https://learn.microsoft.com/en-us/azure/container-apps/ingress

### Q-AI200-015 · Develop AI solutions by using Azure data management services · difficulty 2 · scenario

A team stores five million product embeddings of 1,536 dimensions each in Azure Cosmos DB for NoSQL and must serve nearest-neighbour queries with sub-100 ms p95 latency at production scale. Which vector index type should the container's indexing policy declare?

- A) `flat`, because brute-force search always returns the exact nearest neighbours.
- B) `quantizedFlat`, because it stores quantized vectors on the same index as other indexed properties.
- C) `diskANN`, because it is an approximate nearest-neighbour index designed for large-scale vector search with a memory-bounded graph structure.
- D) No vector index, because `VectorDistance` scans the container regardless of how the policy is written.

<details><summary>Answer</summary>

**C.** `diskANN` is the index built for this scale. `flat` is a brute-force scan with 100 percent recall but a hard ceiling of 505 dimensions and a cost that grows with the corpus. `quantizedFlat` is also a brute-force search over quantized vectors, cheaper than `flat` but still linear, and Microsoft recommends it when the search is scoped to roughly 50,000 vectors or fewer. `diskANN` trades a small amount of recall for a large reduction in latency and request units once the corpus is in the millions, and it accepts up to 4,096 dimensions.

- Why not A: `flat` cannot exceed 505 dimensions, so it is not even a legal choice for a 1,536-dimension embedding, and its brute-force cost is prohibitive at five million vectors.
- Why not B: `quantizedFlat` improves latency and RU cost relative to `flat` but does not change the linear cost in corpus size, and it is not the recommended option beyond roughly 50,000 vectors.
