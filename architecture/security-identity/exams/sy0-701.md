## Domain 1.0: General Security Concepts (12% Weight · Questions 001–010)

### Q-SY0-701-001 · Domain 1.0 · difficulty 1 · single
Which core tenet of the CIA Triad is directly violated when an attacker performs a bit-flip attack on an unauthenticated ciphertext stream encrypted using AES in Counter (CTR) mode without a message authentication code?
- A) Confidentiality
- B) Integrity
- C) Availability
- D) Non-repudiation
<details><summary>Answer</summary>

**B.** In stream ciphers or stream modes like AES-CTR without authentication, flipping a bit in the ciphertext produces an identical, predictable bit-flip in the decrypted plaintext ($C'_i = C_i \oplus \Delta \implies P'_i = P_i \oplus \Delta$). This violates **Integrity** while preserving the stream's confidentiality (the key is not disclosed). Authenticated Encryption with Associated Data (AEAD) is required to guarantee integrity.
- Why not A: The plaintext is not directly disclosed to eavesdroppers simply by flipping bits.
- Why not C: Availability concerns system downtime or resource exhaustion, not bit manipulation.
- Why not D: Non-repudiation prevents a party from denying an action they performed (typically backed by digital signatures).
- Ref: [modules/01-threat-modeling-and-security-principles.md](../modules/01-threat-modeling-and-security-principles.md#the-cia-triad--parkerian-hexad), [modules/02-crypto-primitives-for-engineers.md](../modules/02-crypto-primitives-for-engineers.md#authenticated-encryption-with-associated-data-aead)
</details>

### Q-SY0-701-003 · Domain 1.0 · difficulty 2 · scenario
An infrastructure engineer proposes generating session tokens using JavaScript's native `Math.random()` inside a high-throughput Node.js microservice. Why does this create a critical security vulnerability?
- A) `Math.random()` blocks the Node.js event loop during high concurrent traffic.
- B) `Math.random()` relies on the xorshift128+ PRNG algorithm, which allows an attacker observing a sequence of outputs to reconstruct internal state and predict all future session tokens.
- C) `Math.random()` produces floating-point numbers that cannot be encoded as hexadecimal or base64 strings.
- D) `Math.random()` generates tokens with an entropy of only 8 bits per invocation.
<details><summary>Answer</summary>

**B.** `Math.random()` uses pseudo-random number generators (PRNGs) such as xorshift128+ in V8. These algorithms are designed for statistical uniform distribution and speed in games/simulations, not cryptographic unpredictability. An attacker observing as few as two to three consecutive outputs can solve the linear equations to reconstruct the PRNG's internal state and forge future session tokens. Cryptographic systems must use CSPRNGs like `crypto.randomBytes()` or `crypto.getRandomValues()`.
- Why not A: `Math.random()` is extremely fast and non-blocking.
- Why not C: Floats can easily be mapped to integers and encoded, but that does not fix the predictability.
- Why not D: It outputs 53 bits of precision (IEEE 754 double), not 8 bits, but it has zero cryptographic security.
- Ref: [modules/02-crypto-primitives-for-engineers.md](../modules/02-crypto-primitives-for-engineers.md#prng-vs-csprng-entropy-and-unpredictability)
</details>

### Q-SY0-701-004 · Domain 1.0 · difficulty 2 · multi
Which of the following properties are essential requirements for a secure cryptographic hash function suitable for digital signatures and commitment schemes? (Select TWO)
- A) Pre-image resistance (one-wayness: given $y$, it is computationally infeasible to find $x$ such that $H(x) = y$).
- B) Reversibility (given $H(x)$ and an escrow key, $x$ can be reconstructed in polynomial time).
- C) Collision resistance (it is computationally infeasible to find any distinct pair $x_1 \neq x_2$ such that $H(x_1) = H(x_2)$).
- D) Linear homomorphic additivity ($H(a + b) = H(a) + H(b)$).
<details><summary>Answer</summary>

**A, C.** A cryptographic hash function must satisfy: (1) Pre-image resistance (one-way), (2) Second pre-image resistance (given $x_1$, finding $x_2$ such that $H(x_1)=H(x_2)$ is infeasible), and (3) Collision resistance (finding any colliding pair is infeasible).
- Why not B: Cryptographic hash functions must be strictly non-reversible; escrow keys apply to encryption, not hashing.
- Why not D: Linear homomorphic properties are specific to homomorphic ciphers; in standard hashes, linearity would allow trivial collision generation and algebraic attacks.
- Ref: [modules/02-crypto-primitives-for-engineers.md](../modules/02-crypto-primitives-for-engineers.md#cryptographic-hash-functions-and-collision-resistance)
</details>

### Q-SY0-701-005 · Domain 1.0 · difficulty 2 · single
When storing user passwords in an authentication database, why is SHA-256 (even when combined with a unique salt) considered completely inadequate by OWASP and NIST guidelines?
- A) SHA-256 suffers from practical collision attacks that allow rainbow tables to reverse salted inputs.
- B) SHA-256 is designed for fast hardware execution ($>10^9$ hashes/sec on modern GPUs/ASICs), allowing attackers to execute high-velocity offline brute-force attacks against dumped databases.
- C) Salted SHA-256 produces variable-length outputs that corrupt database indexes.
- D) SHA-256 requires specialized hardware acceleration that is unsupported on Linux kernels.
<details><summary>Answer</summary>

**B.** General-purpose cryptographic hash functions (SHA-256, SHA-3) are engineered for maximum throughput when hashing gigabytes of network packets or file blocks. A modern GPU cluster can compute tens of billions of SHA-256 hashes per second. Password storage requires intentionally slow, memory-hard Key Derivation Functions (KDFs) like **Argon2id** (RFC 9106), **scrypt**, or **bcrypt** that consume massive memory buffers (e.g., 64 MiB RAM per hash) to neutralize GPU/ASIC parallelization.
- Why not A: SHA-256 has no known collision attacks, but brute-forcing low-entropy passwords does not require mathematical hash collisions.
- Why not C: SHA-256 always produces fixed 32-byte (256-bit) digests.
- Why not D: SHA-256 is universally supported across all platforms.
- Ref: [modules/03-passwords-and-secrets-at-rest.md](../modules/03-passwords-and-secrets-at-rest.md#why-general-purpose-hashes-fail-for-passwords)
</details>

### Q-SY0-701-007 · Domain 1.0 · difficulty 2 · scenario
An authentication service uses `crypto.timingSafeEqual()` in Node.js to compare user-supplied API keys against stored HMAC digests. A developer accidentally passes two buffers of different byte lengths to `timingSafeEqual()`. What occurs?
- A) The function returns `false` in constant time.
- B) The function throws a `RangeError` exception immediately, leaking the length of the secret buffer to an attacker via timing discrepancies.
- C) The function silently pads the shorter buffer with zero bytes.
- D) The function performs an XOR comparison up to the length of the shorter buffer.
<details><summary>Answer</summary>

**B.** `crypto.timingSafeEqual(a, b)` requires that `a.byteLength === b.byteLength`. If the lengths differ, it immediately throws `RangeError: Input buffers must have the same byte length`. If an application blindly calls this without first verifying length or hashing inputs with HMAC, the exception timing leaks buffer length to an adversary. Secure systems hash both values (e.g. with HMAC-SHA256) first before comparing, guaranteeing equal-length inputs.
- Why not A: It does not return `false`; it throws an immediate runtime exception.
- Why not C, D: Cryptographic libraries never guess or silently pad buffers.
- Ref: [modules/02-crypto-primitives-for-engineers.md](../modules/02-crypto-primitives-for-engineers.md#timing-attacks-and-constant-time-comparisons)
</details>

### Q-SY0-701-009 · Domain 1.0 · difficulty 2 · single
What cryptographic mechanism allows a client to verify whether a user's password exists in a database of compromised credentials (such as Have I Been Pwned) without disclosing the user's password or its full hash to the remote server?
- A) Blind RSA Signatures
- B) k-Anonymity using SHA-1 / SHA-256 hash prefix querying
- C) Diffie-Hellman Key Exchange
- D) Homomorphic Paillier Encryption
<details><summary>Answer</summary>

**B.** **k-Anonymity** via hash prefix matching allows the client to calculate the SHA-1 or SHA-256 hash of the password, send only the first 5 hexadecimal characters (20 bits of entropy) to the API, and receive a list of all hash suffixes sharing that prefix. The client searches the returned suffixes locally. The remote server only learns that the password falls into a bucket of thousands of candidate passwords, never the actual password.
- Why not A: Blind RSA is used in anonymous tokens and e-cash, not database prefix lookups.
- Why not C: Diffie-Hellman establishes shared secret keys over insecure channels.
- Why not D: Homomorphic encryption is computationally overkill and not how breached password checks are implemented.
- Ref: [modules/03-passwords-and-secrets-at-rest.md](../modules/03-passwords-and-secrets-at-rest.md#k-anonymity-and-have-i-been-pwned-hibp-queries)

### Q-SY0-701-012 · Domain 2.0 · difficulty 2 · scenario
To mitigate SSRF, an engineer implements a domain allowlist that performs a DNS lookup on the user-supplied hostname and checks if the resolved IP address is in a private IP range. An attacker registers domain `evil.attacker.com` with a DNS TTL of 0 seconds. On the first lookup during validation, it returns a public IP `198.51.100.1`. When the HTTP client connects 1 millisecond later, the DNS server returns `127.0.0.1`. What technique defeated the filter?
- A) HTTP Request Smuggling
- B) DNS Rebinding
- C) ARP Poisoning
- D) Cache Poisoning
<details><summary>Answer</summary>

**B.** **DNS Rebinding** exploits the Time-of-Check to Time-of-Use (TOCTOU) gap between the initial IP validation step and the actual socket connection. By returning a benign IP with TTL 0 on the first query and an internal IP (`127.0.0.1` or `169.254.169.254`) on the subsequent connection query, the attacker bypasses hostname validation. Mitigation requires pinning the validated IP address at the socket connection layer.
- Why not A: Request smuggling exploits discrepancies between frontend and backend HTTP parsers.
- Why not C: ARP poisoning operates at Layer 2 on local broadcast segments.
- Why not D: Cache poisoning injects malicious responses into intermediate proxy caches.
- Ref: [modules/11-web-and-api-vulnerability-classes.md](../modules/11-web-and-api-vulnerability-classes.md#dns-rebinding-attacks)

### Q-SY0-701-015 · Domain 2.0 · difficulty 3 · scenario
A resource server uses an asymmetric RSA key pair (RS256) to sign and verify JWT access tokens, publishing its public key via a JWKS endpoint. An attacker crafts a forged JWT with header `{"alg": "HS256"}` and signs it using the server's public RSA key (in PEM/SPKI text format) as the HMAC shared secret. If the server verifies tokens using a dual-mode function that blindly accepts the algorithm specified in the token header, what vulnerability is exposed?
- A) Bleichenbacher RSA padding oracle
- B) RS256 / HS256 Algorithm Confusion (Key Confusion)
- C) Length Extension Attack
- D) Golden SAML attack
<details><summary>Answer</summary>

**B.** In the **RS256/HS256 Algorithm Confusion** attack, the attacker changes the header algorithm from asymmetric RS256 to symmetric HS256. When the vulnerable server verifies the token using its public key, the HMAC library treats the public key bytes as the secret key. Because the public key is known to everyone, the attacker signs the forged token with that public key and the server validates it successfully. Defense requires pinning algorithms explicitly (`algorithms: ["RS256"]`).
- Why not A: Bleichenbacher attacks exploit PKCS#1 v1.5 RSA decryption padding errors.
- Why not C: Length extension attacks exploit Merkle-Damgård hashes without HMAC construction.
- Why not D: Golden SAML involves forging SAML assertions after stealing an Active Directory Federation Services (ADFS) signing certificate.
- Ref: [modules/08-tokens-jose-and-sender-constraining.md](../modules/08-tokens-jose-and-sender-constraining.md#algorithm-confusion-rs256-vs-hs256)
</details>

### Q-SY0-701-021 · Domain 2.0 · difficulty 2 · single
What attack allows an adversary to recover the XOR difference of two plaintexts ($P_1 \oplus P_2$) when an application uses AES-GCM?
- A) Padding Oracle attack
- B) Nonce Reuse Catastrophe
- C) Bit-flip MAC forgery
- D) Length extension attack
<details><summary>Answer</summary>

**B.** In AES-GCM (which uses CTR mode for encryption), if the same $(K, N)$ key-nonce pair is used to encrypt two different plaintexts $P_1$ and $P_2$, the counter keystream $S$ is identical: $C_1 = P_1 \oplus S$ and $C_2 = P_2 \oplus S$. Computing $C_1 \oplus C_2 = (P_1 \oplus S) \oplus (P_2 \oplus S) = P_1 \oplus P_2$. If an attacker knows or guesses one plaintext, they immediately recover the other. Furthermore, in GCM, nonce reuse allows an attacker to solve polynomial equations over $\text{GF}(2^{128})$ to recover the GHASH authentication key $H$, forging arbitrary authentication tags.
